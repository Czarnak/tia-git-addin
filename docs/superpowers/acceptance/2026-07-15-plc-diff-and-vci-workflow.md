# Acceptance Criteria: PLC Diff and VCI Git Workflow

**Spec:** `docs/plans/2026-07-15-plc-diff-and-vci-workflow-design.md`

**Status:** Approved

## Criteria

For this Windows desktop project, `UI interaction` criteria are executed through
the named live-TIA V21 runbook. WPF behavior that can run through xUnit/STA tests is
classified as `Logic`.

| ID | Description | Test Type | Preconditions | Expected Result |
|----|-------------|-----------|---------------|-----------------|
| AC-001 | The documented V21 comparison decision is authoritative, complete, and consistent across the investigation, PRD, and README. | Logic | The three documents, installed V21 public XML/help sources, and inspected public assemblies are available. | The investigation identifies the V21 build, public XML files, help topic IDs, and public assembly file versions/SHA-256; its matrix covers PlcSoftware.CompareTo, CompareToOnline, hardware/library comparison, mapped-object status, result shape, input limits, and permissions; internal metadata is labeled boundary evidence only; all three documents select the project-owned comparer with explicit fallback and make no conflicting API claim. |
| AC-002 | Production code does not reference internal Siemens comparison assemblies or types. | Logic | The repository source tree is available. | A case-insensitive scan of tracked production files under src finds zero references to Siemens.Automation.CommonServices.Compare, CompareEditorStarter, or reflection-based equivalents. |
| AC-003 | Project references preserve the Siemens-free Core boundary. | Logic | All project files are available. | TiaGitAddIn.Core builds for netstandard2.0 with zero Siemens or WPF references; only TiaGitAddIn contains TIA/Add-In references. |
| AC-004 | The integration-test project remains independent of WPF and Siemens assemblies. | Logic | TiaGitAddIn.IntegrationTests exists. | Its project references include TiaGitAddIn.Core and test packages only; it does not reference TiaGitAddIn or any Siemens assembly. |
| AC-005 | Automated and live acceptance lanes state their different VCI boundaries accurately. | Logic | The design, README test instructions, and live runbook exist. | Automated documentation says the test begins with a fixture workspace change; the live runbook alone claims actual project-to-workspace synchronization. |
| AC-006 | Git revision review does not open a second TIA project or invoke PlcSoftware.CompareTo. | Logic | Production comparison code is implemented. | Static inspection and comparison integration tests show no TiaPortal/project creation and no CompareTo or CompareToOnline call in the Git diff path. |
| AC-007 | Comparison domain objects and parsed inputs remain immutable across comparisons. | Logic | Tests retain parser models and every result/presentation variant across repeated comparisons. | Constructor inputs are defensively copied, exposed collections are read-only, parsed models remain unchanged, and neither later comparisons nor mutations of original input collections change an earlier result. |
| AC-008 | Strategy selection is centralized and every result contains one typed presentation rather than being routed through LAD. | Logic | The coordinator is given representative LAD, FBD, interface, SCL, text, unsupported, and error inputs. | The coordinator selects exactly one compatible strategy or fallback; each result contains the matching sealed presentation type, ViewModels contain no duplicate artifact classifier, and no non-LAD artifact produces a LAD presentation. |
| AC-009 | Revision loading preserves working-tree and committed artifact identity and bytes. | Logic | The same UTF-8 fixture exists in the working tree and a commit under a non-XML suffix. | Both loaded revisions report the original path and suffix and expose byte-for-byte identical content. |
| AC-010 | Supported text encodings decode without data loss. | Logic | Equivalent strict UTF-8, UTF-8 BOM, UTF-16 LE BOM, and UTF-16 BE BOM fixtures are available. | Each fixture yields the expected Unicode text and encoding metadata with zero replacement characters. |
| AC-011 | Invalid text bytes are never silently replacement-decoded. | Logic | A committed blob contains invalid strict UTF-8 and no recognized BOM. | The revision is classified binary or unsupported, decoded text is absent, and a non-empty encoding limitation is returned. |
| AC-012 | Added and deleted artifacts retain an explicit missing-side reason and classify from the available side. | Logic | One comparison pair is left-missing and another is right-missing, with the available sides containing known artifact markers. | The first resolves as Added and the second as Removed; each pair kind/mode matches the available side and neither fabricates empty content as a present revision. |
| AC-013 | Configured revision-size limits stop oversized input before parsing. | Logic | The provider is configured with maximum size N and receives otherwise valid N-byte and N-plus-one-byte revisions. | The N-byte revision loads; the larger revision is not parsed, returns an Error presentation with a size-limit diagnostic, and invokes no comparison strategy. |
| AC-014 | Content-aware classification recognizes supported LAD, FBD, and SCL artifacts. | Logic | Sanitized fixtures include neutral VCI paths with authoritative LAD/FBD content markers and an .scl source with valid lexical evidence. | The fixtures resolve respectively to LAD Visual, FBD Visual, and SCL Structured preferred modes without requiring language words in directory names. |
| AC-015 | Generic XML receives explicit text fallback. | Logic | Both sides are well-formed XML without known SimaticML namespaces or PLC block markers. | The result is GenericXml, Text, Fallback with a non-empty limitation; no PLC visual model is created. |
| AC-016 | Unsupported STL and SFC artifacts receive explicit text fallback. | Logic | Valid textual STL and SFC fixtures are provided without semantic strategies. | Each result is Text, Fallback, identifies its artifact kind, and states that semantic comparison is unavailable. |
| AC-017 | Conflicting side classifications do not invoke either semantic strategy. | Logic | The left side classifies as FBD and the right side as SCL. | The pair returns Text, Fallback with a classification-conflict diagnostic and retains both raw sides. |
| AC-018 | Malformed text-based PLC artifacts fall back with diagnostics. | Logic | A recognized SimaticML or SCL artifact contains a deterministic syntax error. | The coordinator returns Text, Fallback, a non-empty parse diagnostic with safe source location, and the raw diff remains available. |
| AC-019 | Recoverable unknown structure remains a partial semantic result. | Logic | A valid FBD graph contains one unknown but bounded Part alongside known nodes. | The result is Visual · Partial, contains a generic node for the unknown Part, and shows a non-empty limitation. |
| AC-020 | Binary content is reported unsupported. | Logic | At least one side contains NUL/binary data and binary evidence is set by the revision provider. | The result is Unsupported, Unsupported with no decoded text presentation and a non-empty limitation. |
| AC-021 | Revision-loading failure is a hard error rather than fallback. | Logic | The requested commit or file cannot be read. | The coordinator returns an Error presentation, does not run semantic or text comparison, and reports the load failure safely. |
| AC-022 | Mode and support are displayed as separate values. | Logic | Full visual, partial structured, text fallback, and unsupported result ViewModels are created. | Their headers read Visual · Full, Structured · Partial, Text · Fallback, and Unsupported · Unsupported respectively. |
| AC-023 | Raw text remains selectable for every successfully decoded text artifact. | Logic | Visual, structured, partial, and fallback text-based results are loaded. | Each exposes a selectable raw-text presentation containing both sides or the Git patch; binary and hard-error results do not claim raw text. |
| AC-024 | Working-tree and committed comparisons route identically. | Logic | Identical artifact bytes are loaded once from the working tree and once from a commit with the same original path. | Artifact kind, mode, support level, limitation, and semantic changes are equal between both comparisons. |
| AC-025 | A newer selection prevents an older result from updating the UI. | Logic | Selection A is delayed, selection B completes first, and both use controllable tasks. | A is cancelled or rejected by generation check; only B becomes CurrentComparison and no A-derived property change occurs afterward. |
| AC-026 | Async void is confined to genuine WPF event boundaries. | Logic | The modified ViewModels and services are available for static inspection. | Comparison/loading methods return Task and accept CancellationToken; every remaining async void method has a WPF event-handler signature. |
| AC-027 | UI-bound comparison state is updated on the dispatcher. | Logic | A comparison completes on a background thread in an STA ViewModel test. | Property changes for the current result execute on the captured dispatcher thread and do not raise a cross-thread exception. |
| AC-028 | WPF DataTemplates resolve every presentation kind. | Logic | The application resources and representative ViewModels are loaded in an STA test. | Interface, FBD, SCL, text, unsupported, and error presentations each resolve to their dedicated view type with no missing-resource exception. |
| AC-029 | Partial, fallback, and unsupported results show limitations inline. | Logic | Representative ViewModels for all support levels are bound to their views. | Full results hide the limitation panel; Partial, Fallback, and Unsupported results show non-empty mode-specific limitation text. |
| AC-030 | Expandable UI diagnostics omit sensitive implementation details. | Logic | Diagnostics contain a stack trace, credential-bearing URL, and temporary path before sanitization. | The visible details retain the stable code and safe location but contain no stack trace, URL user information, credential token, or temporary path. |
| AC-031 | New focused WPF controls remain within the repository file-size limit. | Logic | Interface, FBD, SCL, and shared comparison XAML/ViewModel files are implemented. | Every touched focused source/XAML file contains at most 800 lines and no new artifact-specific UI is appended to the monolithic LAD view. |
| AC-032 | Every focused comparison view constructs and binds at runtime. | Logic | STA smoke fixtures provide representative full, partial, fallback, and malformed-input ViewModels. | Each view initializes, resolves resources/templates, applies bindings, and disposes without binding errors or unhandled exceptions. |
| AC-033 | Visual status is not communicated by color alone. | Logic | Added, removed, modified, and rewired FBD elements are rendered. | Every status has a visible label, icon, stroke pattern, or equivalent non-color cue in addition to its color. |
| AC-034 | Interface datatype, Retain, default, and StartValue normalization and changes follow the field matrix. | Logic | Independent fixtures cover datatype outer whitespace and internal-text differences; default/StartValue outer whitespace, line-ending, and internal-text differences; and every true/false/unspecified Retain pairing. | Datatype outer trim alone compares equal while every internal datatype difference changes; default/StartValue outer or line-ending normalization compares equal while every internal value difference changes; every distinct Retain state pairing reports one Modified member and only the affected field is marked while both values remain available. |
| AC-035 | Multilingual interface comments compare by language. | Logic | Comment fixtures vary line endings, trailing line whitespace, language key, and text. | Normalized whitespace-only variants compare equal; changed text or an added/removed language entry reports the exact language-level change. |
| AC-036 | Accessibility, Informative, Version, and whitelisted semantic attributes follow their declared normalization. | Logic | Fixtures independently cover known/unknown accessibility text, every true/false/unspecified Informative pairing, outer-whitespace Version variants, and typed equivalent/different whitelisted values. | Unknown accessibility text is preserved and compared exactly, distinct Informative states change, trimmed-equal Version values do not change, typed-equivalent whitelist values compare equal, typed-different values change, and non-whitelisted attributes are ignored. |
| AC-037 | Volatile interface metadata does not create changes. | Logic | Two exports differ only in UId, composition identifiers, timestamp/export-order metadata, and document export version. | The interface comparison reports zero changed sections or members. |
| AC-038 | Nested members match by canonical section and NFC-normalized exact-ordinal path. | Logic | The same nested tree uses canonically composed/decomposed Unicode names and different XML ordinals, while a control changes identifier case. | Canonically equivalent names match once without add/remove, XML order is irrelevant, and the case-changed control remains a distinct exact-ordinal path. |
| AC-039 | Empty interface section additions and removals are visible. | Logic | One side contains an empty canonical section and the other does not. | The section is reported Added or Removed even though it contains no members. |
| AC-040 | Interface presentation retains independent left and right snapshots. | Logic | Added, removed, and modified member comparisons are mapped to rows. | Removed rows retain only left values, added rows retain only right values, and modified rows expose both without right-first collapsing. |
| AC-041 | Interface additions, removals, and section moves retain complete subtrees. | Logic | One parent with nested children exists on only one side and another member moves between canonical sections. | The one-sided parent change contains its full nested snapshot without duplicate top-level children; the moved member is Removed from the old section and Added to the new section. |
| AC-042 | Interface display order follows the deterministic merge rule. | Logic | Right declarations have order C,A and left-only declarations have order B,D within one section. | The rendered order is C,A followed by B,D while canonical TIA section ordering remains unchanged. |
| AC-043 | Pure interface reordering and unchanged interfaces produce no false changes. | Logic | One pair differs only in member order and another is byte-different but semantically identical. | Both comparisons report zero changed fields, members, and sections while retaining complete snapshots. |
| AC-044 | Sanitized V21 FBD exports build a neutral semantic graph. | Logic | Manifest-validated real V21 fixtures contain accesses, Parts, Calls, rails, branches, and wires. | The graph contains the expected block/network counts and typed nodes, pins, and edges declared by each manifest. |
| AC-045 | FBD pins and edges retain connector semantics. | Logic | A fixture contains named inputs, outputs, branches, and a disconnected/open connector. | Connector name and direction are preserved; connected edges reference the correct node/pin endpoints and the open connector remains unconnected. |
| AC-046 | FBD blocks and networks match by stable semantic keys independently of list index. | Logic | Two files contain the same multiple blocks/networks in different serialization order and the key builder runs repeatedly. | Each block/network key is identical across runs and sides, each semantic pair matches once, and reordering alone produces zero graph changes. |
| AC-047 | FBD UId regeneration does not create changes while UIds remain trace evidence. | Logic | Left and right graphs are semantically identical but every source UId differs. | Parsed nodes retain their side-specific source UId only in trace metadata, semantic identities exclude it, and the comparer reports zero node, pin, and edge changes. |
| AC-048 | FBD node additions, removals, and modifications are distinguished. | Logic | Focused fixture pairs contain exactly one added node, one removed node, or one changed operation/operand. | Each pair produces exactly one change with the expected Added, Removed, or Modified status and no unrelated changes. |
| AC-049 | FBD rewiring is reported explicitly. | Logic | The same matched nodes exist on both sides but one edge endpoint or connector changes. | The result contains one Rewired connection referencing the old and new semantic endpoints rather than an unchanged edge. |
| AC-050 | Ambiguous duplicate FBD nodes are never guessed as modifications. | Logic | Multiple nodes share the same non-unique signature and neighborhood evidence cannot uniquely pair them. | The ambiguous nodes are reported as deterministic additions/removals and no Modified match is invented. |
| AC-051 | Unknown valid FBD Parts render as generic nodes. | Logic | A valid graph includes one unrecognized Part type with known connectors. | The visual model contains a labeled generic function box with its connectors and the overall support level is Partial. |
| AC-052 | Recoverable FBD structure uses the intermediate structured fallback. | Logic | A recognized FBD XML document retains trustworthy block/network/raw-element metadata but cannot produce trustworthy graph connectivity. | The coordinator returns Structured · Partial with the deterministic raw graph summary and a non-empty limitation; it creates no Visual graph presentation and retains raw text. |
| AC-053 | FBD layout is deterministic. | Logic | The same graph is laid out repeatedly and after irrelevant source ordering changes. | Node coordinates, connector ordering, edge routes, and canvas bounds are identical for every run. |
| AC-054 | FBD uses its dedicated view with synchronized navigation and raw text. | Logic | A visual FBD result with changes is loaded in an STA test. | FbdDiffView is selected, left/right navigation state remains synchronized, change cues render, and the raw-text alternative remains selectable. |
| AC-055 | The SCL lexer handles comments, strings, quoted identifiers, and operators without token confusion. | Logic | Fixtures include comment markers inside strings, escaped quotes, line/block comments, and quoted identifiers. | Token kinds and source spans match the manifest; comment text inside strings is not emitted as a comment token. |
| AC-056 | The SCL parser recognizes supported top-level block kinds. | Logic | Fixtures contain an organization block, function block, function, data block, and type block. | One typed syntax node with the expected name and complete source span is produced for each block. |
| AC-057 | SCL declaration sections and declarations retain semantic fields. | Logic | A fixture contains input, output, in-out, static/local, temp, and constant declarations with types/defaults. | Each declaration appears under the expected section with identifier, datatype, modifiers/default, and source span intact. |
| AC-058 | SCL regions, statements, and comments are retained and grouped. | Logic | A block contains nested regions, statements, leading/trailing comments, and code outside a region. | The tree preserves source order, region nesting, statement/comment spans, and an explicit ungrouped bucket for out-of-region code. |
| AC-059 | Every approved SCL recovery boundary retains partial structure and exact unparsed spans. | Logic | A theory supplies separate malformed cases followed respectively by a semicolon, region boundary, declaration terminator, and block terminator, each with known span offsets and valid content afterward. | Each case resumes only at its named boundary, retains the exact malformed span from the manifest, preserves the later valid node, and returns Partial support with one boundary-specific diagnostic. |
| AC-060 | SCL blocks and declarations match by semantic identity. | Logic | Equivalent blocks/declarations are reordered without changing kind, name, section, or tokens. | Each pair matches once and reordering alone produces zero additions/removals. |
| AC-061 | A unique declaration rename is reported as Rename. | Logic | One removed and one added declaration share section, datatype, modifiers, and default while only the identifier differs, with no competing candidate. | The comparer produces exactly one Rename containing both identifiers and no separate add/remove entries for that pair. |
| AC-062 | Ambiguous declaration rename candidates remain additions/removals. | Logic | Two or more removed/added declarations share the same rename fingerprint. | No Rename is produced; all candidates remain deterministic Added or Removed entries. |
| AC-063 | Block-name and region-label changes are not inferred as renames in the initial implementation. | Logic | A top-level block name or region label changes while its body remains otherwise equal. | The result reports Removed and Added groups and contains no Rename for the block or region. |
| AC-064 | Formatting-only SCL whitespace changes are semantically unchanged. | Logic | Token sequences are identical while spaces, indentation, and line endings differ. | Structured comparison reports zero statement changes; the raw-text view still displays the formatting difference. |
| AC-065 | SCL comment changes are reported independently. | Logic | Executable tokens are unchanged while one comment is added, removed, or edited. | The structured result contains only the corresponding comment change and no statement change. |
| AC-066 | SCL partial and fallback thresholds are distinct. | Logic | One fixture yields a recoverable block tree and another cannot establish any reliable block structure. | The first returns Structured · Partial with retained unparsed spans; the second returns Text · Fallback with diagnostics. |
| AC-067 | SCL highlighting and presentation use the comparison lexer tokens. | Logic | A structured result is mapped to the SCL ViewModel and view. | File, block, region, declaration, statement, and ungrouped headers appear in source order, and every highlighted span references the same token kind/span used by comparison. |
| AC-068 | The automated Git lane exercises Core through a test-only process adapter without TIA installed. | API | The integration project is built on a Windows machine with .NET 8 and Git but no TIA/Siemens runtime. | The full integration command exits zero and constructs production GitService with test SystemGitProcessRunner; it does not load Siemens GitProcessRunner or WPF classes. |
| AC-069 | Sequential and concurrent Git workflow runs use isolated short-path repositories. | API | Two sequential and two concurrent fixture instances start with no shared directory. | Every instance receives a distinct working repository and local bare remote, every path remains at most 260 characters, no instance observes another's refs/configuration, and all roots are deleted after completion. |
| AC-070 | Git configuration and credentials are isolated per child process. | API | Host global/system Git settings and a credential helper are deliberately configured. | The child environment sets GIT_CONFIG_NOSYSTEM, a temporary global config, GIT_TERMINAL_PROMPT, and GCM_INTERACTIVE; local signing/hooks/autocrlf settings win and the test never prompts or invokes the host helper. |
| AC-071 | Baseline setup creates deterministic main/upstream state. | API | V1 fixture and empty bare remote exist. | Setup creates main, commits V1 with local identity, runs push with set-upstream, and verifies local main tracks origin/main. |
| AC-072 | The fixture workspace change transitions from unstaged to staged. | API | V2 replaces V1 after baseline push. | GetStatusAsync returns exactly one expected unstaged path; StageAsync moves that same path to staged with no unexpected entries. |
| AC-073 | Commit and history reflect the workspace change. | API | The expected path is staged and a fixed subject is supplied. | CommitAsync succeeds, status is clean, and GetCommitLogAsync returns the new hash and fixed subject at the head. |
| AC-074 | Commit files and diff contain the expected artifact change. | API | The new commit hash is known. | GetCommitFilesAsync contains the artifact once and GetCommitDiffAsync contains the expected V1 removal and V2 addition. |
| AC-075 | Parameterless push updates only the local bare remote. | API | main tracks the local bare origin and the new commit is unpushed. | PushAsync succeeds, remote refs/heads/main equals the new hash, and the remote artifact content equals V2. |
| AC-076 | Automated Git testing uses no external network or real credentials. | API | Network access is unavailable and the remote URL is the local filesystem bare repository. | The complete workflow passes, all configured remotes resolve inside the test root, and captured transcripts contain no credential prompt or network URL. |
| AC-077 | Git failures emit bounded, redacted, phase-specific diagnostics. | API | A controlled process runner fails the Commit phase with exit code 128, stderr marker controlled-failure, known stdout, and a fixed elapsed duration. | Output identifies Commit, exit 128, controlled-failure, Git version, redacted command/arguments, working directory, bounded stdout/stderr, fixed elapsed duration, and test root; URL user information and credential-like values are absent. |
| AC-078 | Git fixture cleanup always runs and handles transient locks. | API | Success, command failure, assertion failure, an injectable deletion boundary that throws IOException exactly N times then succeeds, a boundary that exceeds the retry budget, a local keep-temp run, and a CI-mode keep-temp run are exercised. | Disposal runs in every case; the N-failure boundary succeeds on retry N-plus-one, the exhausted boundary fails with its retained path, one real-filesystem cleanup smoke passes, local TIA_GIT_E2E_KEEP_TEMP=1 preserves/reports the root, and CI ignores that variable and deletes. |
| AC-079 | GitE2E categorization and developer commands are documented. | Logic | README and the integration test project are present. | The workflow test has Category GitE2E and README contains the approved focused and full dotnet test commands verbatim with the no-TIA automated boundary stated. |
| AC-080 | Live acceptance installs the exact candidate artifact. | UI interaction | A candidate package, candidate run/artifact ID, and SHA-256 are available. | The installed package identity and recomputed SHA-256 equal the recorded candidate values before TIA testing starts. |
| AC-081 | Required TIA permissions are confirmed in the live environment. | UI interaction | A fresh TIA V21 instance loads the candidate Add-In. | TIA.ReadWrite and ProcessStartPermission are approved and recorded; denial causes the run to fail before Git operations. |
| AC-082 | The live fixture establishes a mapped V1 workspace file. | UI interaction | A fresh TiaGitAcceptance project copy, Program mapping, workspace, and bare remote exist. | Built-in Project to workspace synchronization creates Program.xml at the mapped path containing GitAcceptanceV1 and records its hash. |
| AC-083 | Live TIA performs the actual V2 project-to-workspace synchronization. | UI interaction | The project marker is changed from GitAcceptanceV1 to GitAcceptanceV2 inside TIA. | Built-in synchronization changes Program.xml, its hash differs from V1, and its decoded content contains GitAcceptanceV2. |
| AC-084 | The packaged Add-In resolves the VCI repository and completes status, stage, commit, history, and diff. | UI interaction | AC-083 has produced the only workspace change and the mapped workspace item is selected. | Open Git Panel resolves the intended repository and shows the expected unstaged/staged transitions, fixed-subject commit, clean status, history head, and V1-to-V2 diff without permission or assembly failure. |
| AC-085 | The packaged Add-In pushes live acceptance without credentials. | UI interaction | main tracks the local bare origin and the V2 commit is local. | Parameterless push succeeds, the remote main hash equals the V2 commit, and remote Program.xml contains GitAcceptanceV2 without a credential prompt. |
| AC-086 | Live evidence is schema-valid and sanitized. | Logic | A passing and failing live evidence bundle each contain summary, transcript, and Add-In log, including a failure before remote creation. | summary.md records pass/fail, source commit, candidate ID, package hash, TIA/API versions, reviewer, permissions, and log/transcript references; remoteHash is the verified hash after remote creation or literal not-reached with failedStep for an earlier failure; validation rejects credentials, URL user information, private identifiers, network addresses, and machine-specific private paths. |
| AC-087 | Live cleanup occurs only after TIA releases files. | UI interaction | Evidence has been captured and the project/workspace exist. | The run saves/closes the project, closes TIA, waits for process exit, then retry-deletes project copy, workspace, and bare remote; preservation occurs only by explicit local choice. |
| AC-088 | Live smoke and final release acceptance are both recorded in sequence. | Logic | The first packaged Git lane and a final release candidate are available. | A dated smoke evidence record predates final integration and a separate passing final record references the release candidate and predates publication. |
| AC-089 | Release publication uses only passing evidence and the single accepted candidate without rebuilding. | API | Tests pass and publication is attempted with controlled cases for pass/fail outcome, reviewer present/missing, approval granted/pending/rejected, evidence/candidate/tag commit match/mismatch, and package hash match/mismatch. | Only pass evidence with reviewer, matching source/tag/candidate provenance, matching hash, and authorized protected approval publishes the stored candidate; every negative case publishes nothing, and no publication case invokes build/publisher commands. |
| AC-090 | Both test projects pin the approved coverage integration. | Logic | Unit and integration project files are present. | Each references coverlet.msbuild version 6.0.4 with PrivateAssets all and no conflicting coverage collector version. |
| AC-091 | Coverage from net48 and net8 tests is merged over the approved production scope. | API | Release build outputs and both test projects are available. | The net48 run emits JSON with AppDomain disabled; the net8 run merges it and emits merged JSON plus TestResults/Coverage/coverage.cobertura.xml containing TiaGitAddIn.Core and designated testable TiaGitAddIn production classes from both runs. |
| AC-092 | CI enforces exactly 80 percent total line coverage. | API | Controlled merged reports represent 79.99 and 80.00 percent total line coverage. | The invoked properties are Threshold=80, ThresholdType=line, and ThresholdStat=total; the 79.99 report exits nonzero and the 80.00 report exits zero. |
| AC-093 | Coverage exclusions cannot hide ordinary production code. | Logic | Coverage configuration is available. | Exclusions name only generated g.cs/g.i.cs output, GeneratedCode/CompilerGenerated attributes, or individually justified Siemens bootstrap files; no broad production directory exclusion exists. |
| AC-094 | The reusable test gate runs every required phase before candidate creation and non-release triggers cannot publish. | API | Pull-request, main-push, and release-candidate workflow definitions are exercised, and each required phase is forced to fail once. | Every trigger runs restore, Release build, net48 tests, unfiltered Category GitE2E net8 tests, JSON merge, 80 percent threshold, and Cobertura upload; each failure blocks downstream work, successful PR/main runs upload coverage but never a candidate, and only a passing candidate run uploads the package. |
| AC-095 | XML parsing prohibits external entities and DTD processing. | Logic | A SimaticML fixture contains an inline DTD and external entity URI. | Parsing rejects the document without resolving the URI or reading external content and returns a safe diagnostic/fallback. |
| AC-096 | Parser token and nesting limits are enforced deterministically. | Logic | XML/SCL parsers are configured with limits N and receive otherwise valid inputs at N and N-plus-one. | Input at N is processed successfully; input above N stops at the boundary, returns a limit diagnostic, and does not continue allocating nodes/tokens. |
| AC-097 | Git paths and revisions cannot be interpreted as shell syntax or options. | Logic | Inputs include spaces, quotes, leading dashes, traversal, and shell metacharacters. | Pathspec-taking commands pass valid repository-relative names as discrete arguments after a literal -- separator; revision-taking commands pass validated revisions as discrete arguments; traversal/invalid revisions are rejected, no shell is launched, and no unintended command executes. |
| AC-098 | Logs and UI redact credential-like data consistently through the logging boundary. | Logic | Errors contain URL user information, token/password-shaped values, stack traces, and temporary paths. | User-visible output removes all four categories; detailed internal context is emitted only through IAddInLogger, and captured logs contain approved context but no credential-like value. |
| AC-099 | Temporary revision resources are unique and deterministically disposed. | Logic | Concurrent successful, failed, and cancelled commit comparisons are executed. | Each uses a distinct scoped location, all leases dispose in finally paths, and no temporary revision file remains after the operation. |
| AC-100 | Fixture manifests record provenance and sanitization. | Logic | All committed FBD, SCL, and VCI workflow fixtures are enumerated. | Every fixture has manifest entries for V21 API build, kind, encoding/BOM, sanitization actions, SHA-256, and expected support level; hashes match the files. |
| AC-101 | Fixture sanitization rejects sensitive or machine-specific content. | Logic | A control fixture contains a forbidden customer/device identity, IP/network address, credential marker, or absolute machine path. | The sanitization test fails for the control and passes for every committed real/synthetic fixture. |
| AC-102 | Sanitized real V21 fixtures anchor FBD and SCL acceptance. | Logic | Real and synthetic fixture manifests are available. | At least one manifest-validated real V21 FBD export and one real V21 SCL export pass their parser/comparer compatibility tests; synthetic fixtures alone cannot satisfy this criterion. |
| AC-103 | Final verification leaves a releasable, documented repository state. | API | All implementation plans are complete on the integration branch and final live evidence is available. | Existing and new tests pass, merged line coverage is at least 80 percent, the V21 .addin candidate builds, secret/internal-reference scans are clean, graphify update succeeds, the graph report identifies the current source revision, and schema-valid pass evidence matches the candidate hash and source commit. |
| AC-104 | Obsolete SACT terminology and installation guidance are removed from the comparison flow. | Logic | Native SimaticML comparison is wired and production strings/types are scanned. | User-facing messages do not instruct installation of SACT, the active service contract uses project-owned SimaticML naming, and no obsolete SACT dependency is required at runtime. |
| AC-105 | Introducing the neutral FBD graph does not change existing LAD semantics. | Logic | The complete pre-existing LAD regression corpus is run before and after FBD enablement. | LAD comparison states, mapped components/wires, layout outputs, and ViewModel data remain equivalent except for the approved shared result envelope, mode/support, and fallback metadata. |
| AC-106 | The Add-In declares only documented permissions for comparison and Git execution. | Logic | Publisher configuration and the V21 permissions schema are available. | The package declares the required TIA.ReadWrite and ProcessStartPermission entries, declares no invented compare-specific permission, and public in-process comparison evidence does not claim ProcessStartPermission as a compare requirement. |
