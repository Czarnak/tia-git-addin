# PRD: TIA Portal V21 Git Add-In

> Generated by czarnak-workflows /project:prd

## Problem Statement

Automation and PLC engineers working in TIA Portal V21 need proper Git workflows without leaving TIA Portal. Current Siemens-oriented workflows split work across TIA Portal, VCI workspace handling, external Git clients, and external compare tools, which makes commit preparation, history review, pull/push operations, and LAD/FBD change inspection slow and error-prone. The Add-In must make Git a first-class workflow inside TIA Portal V21 while using the TIA VCI workspace as the canonical Git working tree.

## Goals & Success Criteria

- A TIA Portal V21 user can initialize or connect a Git repository for a TIA VCI workspace from inside TIA Portal.
- A user can run core Git operations inside TIA Portal: status, stage, unstage, commit, branch create/switch, fetch, pull, and push.
- A user can browse commit history and inspect files changed in a selected commit.
- A user can compare working tree changes against `HEAD` and compare selected commits against their parent.
- Normal workflows do not open external application windows.
- Git operations show clear success or failure messages and do not corrupt the TIA project or VCI workspace.
- MVP supports at least one tested end-to-end workflow: export or update VCI workspace changes, commit, view commit, inspect diff, and push.
- Automated tests cover core Git service logic, path validation, configuration persistence, and error handling.

## Users

**Primary:** Automation and PLC engineers working in TIA Portal V21 who need to version TIA projects and review changes without leaving TIA.

**Secondary:** Controls team leads or reviewers who inspect commit history, compare block changes, and validate what changed before accepting or integrating work.

## Functional Requirements

1. The Add-In must run inside TIA Portal V21 as a native TIA Add-In.
2. The Add-In must let the user associate the active TIA project with a Git repository.
3. The Add-In must support opening an existing Git repository used for the TIA project.
4. The Add-In must support initializing a new Git repository for the TIA project.
5. The Add-In must use the TIA VCI workspace as the source of truth for files tracked by Git.
6. The Add-In may generate temporary exports for diff or review, but temporary exports must not become canonical repository content unless a later design decision explicitly changes this.
7. The Add-In must detect whether the active project has a supported TIA VCI workspace setup and guide the user when setup is missing or invalid.
8. The Add-In must validate repository and workspace paths and reject unsafe or invalid paths.
9. The Add-In must persist project-level Git configuration without hardcoded machine-specific secrets or credentials.
10. The Add-In must show Git status for the associated repository, including changed, staged, untracked, deleted, and conflicted files.
11. The Add-In must allow staging and unstaging individual files and groups of files.
12. The Add-In must allow committing staged changes with a user-entered commit message.
13. The Add-In must validate commit messages and block empty commits unless the user explicitly enables an advanced option.
14. The Add-In must support fetch, pull, and push from inside TIA Portal without opening external windows.
15. The Add-In must show branch name, remote tracking status, ahead/behind counts, and latest operation result.
16. The Add-In must support creating and switching branches.
17. The Add-In must surface merge conflicts clearly and avoid hiding Git errors behind generic messages.
18. The Add-In must never store Git credentials or provide credential management UI.
19. The Add-In must rely on the user's already configured Git environment and authentication setup.
20. The Add-In must integrate Git by invoking configured local `git.exe`.
21. The Add-In must not implement Git protocol behavior manually.
22. The Add-In must show commit history for the current branch with commit hash, author, date, subject, and changed-file summary.
23. The Add-In must allow selecting a commit and viewing its changed files.
24. The Add-In must allow comparing a selected commit against its parent.
25. The Add-In must allow comparing the working tree against `HEAD`.
26. The Add-In must show text diffs for textual files directly inside TIA Portal.
27. The Add-In must provide TIA-aware comparison for PLC artifacts where possible, especially LAD/FBD blocks.
28. For supported SimaticML LAD revisions, the Add-In must use its embedded, project-owned graphical comparison view inside TIA Portal.
29. When graphical comparison is unsupported or an artifact cannot be parsed, the Add-In must provide a structured or textual fallback inside TIA Portal and clearly identify the limitation.
30. The Add-In must use only documented Siemens Public APIs. V21's data-only comparison APIs may support future live-engineering diagnostics, but the Add-In must not use internal Siemens compare UI/command types for Git revision review. See the [resolved V21 comparison decision](#resolved-decisions).
31. The Add-In must expose functionality through TIA Portal V21 Add-In UI entry points, such as context menu items and/or dockable panes if supported.
32. The Add-In UI must include repository status, staging and commit, branch and remote state, history, commit details, diff viewer, and settings.
33. The Add-In must show long-running Git operations with progress and cancellable or background-safe behavior where supported.
34. The Add-In must prevent conflicting operations, such as push while pull is still running.
35. The Add-In must refresh repository state after Git operations and when relevant TIA project or VCI workspace changes occur.
36. The Add-In must show user-friendly errors in the UI and retain detailed diagnostic logs for troubleshooting.
37. The Add-In must work without requiring a separate companion desktop application.

## Resolved Decisions

- **TIA V21 comparison API (2026-07-15):** V21 exposes supported, in-process, data-only comparison for TIA engineering objects and coarse VCI mapped-object status. It does not expose a supported Add-In surface for Siemens' graphical LAD/FBD compare editor or accept Git/SimaticML revision files. Retain the custom native SimaticML/LAD renderer and the text/structured fallback. See the [investigation and evidence](tia-v21-compare-api-investigation.md).

## Out of Scope

- Built-in Git credential management.
- Git credential storage.
- Hosting or managing remote repositories.
- CI/CD pipeline creation.
- Replacing TIA Portal's project model or bypassing supported Siemens APIs.
- Editing PLC logic directly from the diff or history viewer.
- Embedding or automating Siemens' native graphical compare editor, or claiming Siemens-native comparison fidelity, unless a future supported Public API exposes it.
- Supporting TIA Portal versions before V21.
- Supporting non-Git version control systems.
- Mobile UI, web UI, or standalone companion application.
- Additional installer creation; release artifact is a `.addin` file manually attached to GitHub releases.

## Constraints

- **Tech stack:** C#/.NET TIA Portal V21 Add-In, likely Visual Studio solution structure, using Siemens TIA Openness/Add-In APIs where available.
- **Git backend:** Configured local `git.exe`.
- **Infrastructure:** Windows environment where TIA Portal V21 runs.
- **Deadlines:** None stated.
- **Non-negotiables:** Normal workflows must stay inside TIA Portal and must not open external application windows.
- **Non-negotiables:** No Git credential management or credential storage ever.
- **Non-negotiables:** TIA VCI workspace is the canonical Git working tree.
- **Non-negotiables:** TIA Portal versions before V21 are permanently out of scope because older Openness APIs are incompatible.
- **Versioning strategy:** Target V21 directly for MVP, but isolate Siemens API access behind interfaces so future TIA versions can be added later.
- **Security:** Validate all paths and user inputs; never execute arbitrary user-provided shell text.
- **Testing:** Automated tests required for Git service behavior, path validation, configuration persistence, and error handling.
- **Packaging:** No separate installer; `.addin` file will be manually added to GitHub releases.

## Open Questions
