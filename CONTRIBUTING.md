# Contributing to TIA Git Add-In

Thank you for considering a contribution to **TIA Git Add-In**.

This project is a TIA Portal V21 Add-In for working with Git from inside TIA Portal Version Control Interface (VCI) workflows. Contributions are welcome, but changes must be conservative: this code runs inside an engineering environment and interacts with PLC project data.

## Scope of the project

The project focuses on:

- Git workflow support inside TIA Portal VCI workspaces.
- Native SimaticML parsing and comparison.
- Visual comparison of PLC logic, currently focused on LAD.
- WPF/MVVM UI for Git status, history, commit, and diff workflows.
- Safe, predictable integration with TIA Portal V21 Add-In APIs.

Out of scope unless discussed first:

- Generic Git client features unrelated to TIA Portal / VCI workflows.
- Safety validation, safety acceptance, or certification tooling.
- Changes that require unsupported TIA Portal internals.
- Heavy UI frameworks or dependencies that complicate deployment inside TIA Portal.
- Features that need external runtimes such as Node.js, Python, or background services.

## Repository structure

```text
src/
  TiaGitAddIn/
    TIA Portal V21 Add-In, WPF UI, menu integration, packaging
  TiaGitAddIn.Core/
    Core parsing, comparison, Git/domain logic intended to stay Siemens-API independent
  TiaGitAddIn.Tests/
    xUnit tests for services, configuration, view models, layout, and parsers

graphify-out/
  Optional codebase knowledge graph generated by graphify
```

Keep this separation intact:

- Put reusable domain logic in `TiaGitAddIn.Core` when it does not require TIA Portal APIs.
- Put TIA Add-In integration, WPF views, and TIA-specific entry points in `TiaGitAddIn`.
- Put regression coverage in `TiaGitAddIn.Tests`.

## Development environment

### Required

- Windows.
- TIA Portal V21 installed.
- TIA Portal Openness / Add-In API available from the TIA Portal installation.
- .NET SDK compatible with `global.json`.
- Local Git installation available in `PATH`.
- Visual Studio 2022 or another IDE capable of building .NET Framework 4.8 projects.

### Current target frameworks

- `TiaGitAddIn`: `net48`, WPF, TIA Portal Add-In references.
- `TiaGitAddIn.Core`: `netstandard2.0`.
- `TiaGitAddIn.Tests`: `net48`, xUnit.

### TIA Portal installation path

The Add-In project assumes the default TIA Portal installation path:

```text
C:\Program Files\Siemens\Automation\Portal V21
```

If your installation is elsewhere, pass `TiaPortalInstallRoot` explicitly:

```powershell
dotnet build TiaGitAddIn.sln -p:TiaPortalInstallRoot="D:\Siemens\Automation\Portal V21"
```

## Build

From the repository root:

```powershell
dotnet restore TiaGitAddIn.sln
dotnet build TiaGitAddIn.sln --no-restore
```

The normal build creates the `.addin` package through the Siemens Add-In Publisher:

```text
src/TiaGitAddIn/bin/Debug/net48/TiaGitAddIn.addin
```

To build without packaging, for example while iterating on tests or local code structure:

```powershell
dotnet build TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false
```

This does not remove the requirement for TIA Portal Add-In assemblies when building `TiaGitAddIn`; it only disables the publisher step.

## Test

Run tests from the repository root:

```powershell
dotnet test TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false
```

Before submitting a pull request, run at least:

```powershell
dotnet restore TiaGitAddIn.sln
dotnet build TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false --no-restore
dotnet test TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false --no-build
```

For changes affecting packaging or runtime behavior inside TIA Portal, also run:

```powershell
dotnet build TiaGitAddIn.sln --configuration Release --no-restore
```

and manually verify the resulting `.addin` in TIA Portal V21.

## Manual verification in TIA Portal

For UI, VCI, Git, or packaging changes, include the manual verification result in the pull request.

Recommended smoke test:

1. Build the Add-In package.
2. Copy `TiaGitAddIn.addin` to the TIA Portal Add-Ins folder.
3. Start TIA Portal V21.
4. Activate the Add-In from the Add-ins task card.
5. Open a project with a VCI workspace mapped to a Git repository.
6. Verify that Git menu entries appear for the expected project or VCI selections.
7. Verify at least the affected workflow:
   - status,
   - history,
   - commit,
   - diff,
   - LAD visual diff,
   - repository detection.
8. Check the Add-In log/output for exceptions.

Do not use customer production projects for public bug reports or fixtures. Use sanitized test projects or minimal exported examples.

## Coding guidelines

### General C#

- Keep nullable reference types enabled and fix warnings instead of suppressing them.
- Prefer explicit, small services over large multi-purpose classes.
- Keep side effects isolated, especially file system, Git process, and TIA Portal integration calls.
- Do not hide exceptions silently. Log enough context to diagnose the affected project, file, command, or parser stage.
- Avoid static mutable state unless there is a clear runtime reason.
- Keep public models stable where tests or UI bindings depend on them.

### Git process execution

- Use the existing Git execution/service abstraction instead of invoking Git directly from UI code.
- Do not build shell commands by string-concatenating untrusted paths or user input.
- Prefer argument lists and explicit working directories.
- Treat paths from VCI workspaces as external input.
- Do not perform destructive Git operations without clear UI confirmation.
- Do not store credentials, tokens, passwords, or remote URLs containing credentials.

### SimaticML parsing

- Add tests with minimal SimaticML fixtures for every parser change.
- Preserve unknown XML structures unless there is a documented reason to reject them.
- Do not assume that all TIA Portal exports contain the same XML shape.
- Prefer tolerant parsing with explicit unsupported-state reporting over hard failure.
- Do not introduce external runtime dependencies for SimaticML decoding.

### LAD visualization and diff rendering

- Keep layout, comparison, and rendering concerns separated.
- Add regression tests for branch, rung, contact, coil, box, and powerrail layout changes.
- Avoid hard-coding coordinates when a layout rule would be clearer.
- Keep semantic change coloring consistent:
  - added,
  - removed,
  - changed,
  - unchanged.
- Do not couple visual layout code directly to TIA Portal APIs. It should remain testable outside TIA Portal where possible.

### WPF / MVVM

- Keep business logic out of XAML code-behind.
- Put UI state and commands in view models.
- Avoid blocking the UI thread during Git operations, parsing, or large diff generation.
- Keep dialogs predictable and explicit; do not trigger Git writes from passive UI actions.

## Dependency policy

Dependencies must be justified because they are deployed into a TIA Portal Add-In runtime.

Acceptable dependency reasons:

- Reduces complex, error-prone implementation.
- Is stable, actively maintained, and compatible with .NET Framework 4.8.
- Does not require unmanaged installation steps unless explicitly documented.
- Does not introduce external runtime processes.

Before adding a dependency:

1. Explain why the existing code or BCL is insufficient.
2. Check .NET Framework 4.8 compatibility.
3. Verify that the dependency is copied into the Add-In output when needed.
4. Add or update tests.
5. Document any runtime impact.

## Security and industrial-engineering constraints

This project can interact with engineering data. Treat that as sensitive.

Do not commit:

- Real customer projects.
- Proprietary PLC logic.
- Credentials, tokens, certificates, or private keys.
- Unsanitized SimaticML exports from production machines.
- Build outputs, `.addin` packages, `bin/`, `obj/`, or local TIA Portal caches.

Security-sensitive changes must be explicit in the pull request description. This includes:

- Git command execution.
- File path handling.
- Add-In packaging and dependency loading.
- Parsing of external XML.
- Any feature that writes to a repository or TIA project data.

This project must not be represented as a safety validation or approval tool. Fail-safe program acceptance must remain outside the scope of this Add-In.

## Agent-assisted contributions

This repository contains agent guidance files and a `graphify-out/` knowledge graph.

For architecture or cross-module changes:

1. Review `graphify-out/GRAPH_REPORT.md` if available.
2. Prefer existing service boundaries over creating parallel abstractions.
3. After modifying code files, update the graph if you have graphify installed:

```powershell
graphify update .
```

If you use an AI coding assistant, you are still responsible for reading, testing, and validating the generated changes.

## Branches and commits

Use short, descriptive branch names:

```text
feature/lad-diff-routing
fix/newtonsoft-output-copy
docs/contributing-guide
test/simaticml-fixtures
```

Use imperative commit messages:

```text
Add regression tests for LAD branch layout
Fix Newtonsoft.Json deployment check
Document manual TIA Portal smoke test
```

Keep commits focused. Avoid mixing refactoring, feature work, and formatting-only changes in one commit.

## Pull request checklist

Before opening a pull request, verify:

- [ ] The change has a clear purpose and is scoped to one topic.
- [ ] `dotnet restore TiaGitAddIn.sln` succeeds.
- [ ] `dotnet build TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false --no-restore` succeeds.
- [ ] `dotnet test TiaGitAddIn.sln -p:EnableTiaAddInPackaging=false --no-build` succeeds.
- [ ] New behavior has tests or a clear explanation why automated tests are not practical.
- [ ] TIA Portal V21 manual verification is included when runtime Add-In behavior changed.
- [ ] No customer data, credentials, build outputs, or generated packages are committed.
- [ ] Documentation is updated when behavior, setup, commands, or user workflow changed.

## Releases

Releases are tag-driven.

When preparing a release:

1. Ensure the release build succeeds on a Windows machine with TIA Portal V21 installed.
2. Use a `v*` tag, for example:

```powershell
git tag v1.2.0
git push origin v1.2.0
```

3. The release workflow builds the Add-In package and uploads `TiaGitAddIn.addin` as the release artifact.
4. Keep the tagged commit message useful, because it is used as release-note input.

## Reporting bugs

A useful bug report should include:

- TIA Portal version.
- Add-In version or commit SHA.
- Windows version.
- Git version.
- Whether the project uses VCI workspace mapping.
- Steps to reproduce.
- Expected behavior.
- Actual behavior.
- Sanitized logs or screenshots.
- Minimal sanitized SimaticML sample, if the issue is parser or visual diff related.

Do not attach proprietary project files or customer PLC code.

## Feature requests

For feature requests, describe:

- The engineering workflow problem.
- The current workaround.
- The proposed behavior.
- Whether the feature affects Git operations, SimaticML parsing, LAD/FBD/SCL visualization, or TIA Portal UI integration.
- Any compatibility requirements for TIA Portal versions.
